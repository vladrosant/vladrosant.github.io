01
Personal project · Go · ↗ github

m8s

A Kubernetes-inspired container orchestrator written from scratch in Go, with no framework scaffolding. An API server takes desired state over HTTP, a scheduler assigns workloads to nodes, and a kubelet-style loop reconciles what's running with what should be running.

Go Concurrency Containers net/http Make
Read the case study
Why I built it

I wanted to understand what actually happens between kubectl apply and a running container, and to learn Go properly on a problem where concurrency isn't optional. Reading about control loops is easy; writing one that shuts down cleanly is not.

Architecture

Three components, coordinated through channels and a shared context so a single cancel stops everything in order:

// cmd/ + pkg/ layout, Makefile-driven build apiserver // accepts desired state over HTTP scheduler // assigns workloads to nodes, one goroutine per decision kubelet // reconcile loop: actual vs desired container state select { case <-ctx.Done(): return ctx.Err() case spec := <-desired: reconcile(ctx, spec) }
Lessons

Context propagation is the backbone, not an afterthought: every component that can block needs a way out. Wrapping errors with enough context to know which component failed made debugging the reconcile loop far easier, the same discipline I apply to production Python at work.

02
Open source · PyPI · Claude / MCP · ↗ github

dbt-mcp-server

A Model Context Protocol server that exposes a dbt project's manifest, lineage graph, and test results to Claude, so analysts can ask plain-English questions about dependencies, downstream impact, and missing documentation. Published on PyPI, with external contributors.

Python MCP Claude API dbt manifest.json PyPI
Read the case study
Problem

Even with dbt docs and lineage graphs, certain everyday questions are slow to answer manually: "What's downstream of this source if I rename a column?" · "Which marts have no documentation yet?" · "Why did the test on fct_ad_touchpoints fail this morning?" Clicking through dbt docs is fine; asking is faster.

Approach

Built an MCP server that wraps dbt's manifest.json and run_results.json as a set of tools Claude can call. Each tool answers one specific question and returns structured data the model can summarize naturally.

# Tools exposed by the MCP server get_model_lineage(model_name) # upstream + downstream graph find_orphan_sources() # sources with no downstream models find_undocumented_models() # missing model or column docs summarize_test_failures(since) # last N runs, grouped by model suggest_doc_blocks(model_name) # auto-draft from compiled SQL trace_column_lineage(column, model) # where a column originates
Tech decisions
  • Stateless server: reads target/manifest.json on each tool call so it always reflects the latest dbt parse.
  • Lineage as a graph: parsed once into NetworkX, exposed via subgraph queries.
  • Doc suggestions use Claude itself: server reads a model's compiled SQL, sends it back through the API with a prompt template, returns YAML-ready doc blocks the user can paste into schema.yml.
  • Auth-less local mode for solo devs; HTTP+token mode for team use against a shared dbt project repo.
Lessons

MCP rewards small, sharp tools. The first version had one giant introspect_dbt tool, and it was useless. Splitting it into six narrow tools made Claude's tool selection reliable and the responses crisper. Designing for an agent as the API consumer turned out to be its own discipline.

04
Personal project · Data

ad-attribution-dbt

A modular, multi-client dbt project on BigQuery that unifies LinkedIn Ads, Google Ads, and HubSpot data into a single attribution layer. Per-client schemas isolated via dbt vars, cross-tenant logic encapsulated in macros.

dbt Core BigQuery Jinja GitHub Actions Looker Studio
Read the case study
Why I built it

I wanted a real, multi-source dbt project to learn against, not Jaffle Shop or a one-table tutorial. B2B marketing data was the obvious target: ad platforms, a CRM (HubSpot), and the joins between them are where the actual hard problems live. Multi-client structure was a self-imposed constraint to force me to think about macros and conventions early.

Approach

Three-layer dbt project (staging → intermediate → marts) with a per-client schema convention. Macros handle cross-tenant logic once, parameterized at build time:

-- macros/union_client_sources.sql {% macro union_client_sources(source_name, table_name) %} {% set clients = var('clients') %} {% for client in clients %} select '{{ client }}' as client_id, * from {{ source(source_name ~ '_' ~ client, table_name) }} {% if not loop.last %} union all {% endif %} {% endfor %} {% endmacro %}
Tech decisions
  • Incremental models on all fact tables with merge strategy and event-time-based unique_key.
  • LinkedIn URN extraction macro that pulls campaign / creative / account IDs from URN strings (urn:li:sponsoredCampaign:12345) into clean numeric columns.
  • Google Ads campaign-name parser with regex tokens for account, channel, audience, and geo, surfaced as queryable columns instead of buried in one long name string.
  • dbt_utils / dbt_expectations for referential integrity between deals, contacts, and ad-touchpoint marts.
  • GitHub Actions CI with slim CI (--select state:modified+) so PRs only build affected models against a CI dataset.
