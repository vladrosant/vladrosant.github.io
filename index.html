I started in full-stack web development and moved into data work because the interesting problems kept landing on the database side anyway. The last year and a half has been a slow migration toward the modern data stack: dbt, BigQuery, and the ingestion and visualization tools that sit around them.

What I care about: SQL that explains itself, models that the next person can actually read, and tests that catch the thing you didn't think to check. Dashboards that answer one question well instead of ten questions vaguely.

On the side, I build small tools to make my own work less tedious. It's been the most fun thing I've built this year.

Selected work.

01
Multi-client dbt project · Personal

ad-attribution-dbt

A modular, multi-client dbt project on BigQuery that unifies LinkedIn Ads, Google Ads, and HubSpot data into a single attribution layer. Per-client schemas isolated via dbt vars, cross-tenant logic encapsulated in macros.

dbt Core BigQuery LinkedIn Ads Google Ads HubSpot Looker Studio GitHub Actions Jinja
Read the case study
Problem

A small B2B SaaS team had three ad platforms, a HubSpot CRM, and a single overworked SQL analyst writing 800-line queries by hand for each weekly report. Schema changes in source connectors silently broke dashboards. Multi-client work meant copy-pasting the same query against different schemas.

Approach

Designed a three-layer dbt project (staging → intermediate → marts) with a per-client schema convention. Wrote macros to handle cross-tenant logic once, then parameterize per client at build time:

-- macros/union_client_sources.sql {% macro union_client_sources(source_name, table_name) %} {% set clients = var('clients') %} {% for client in clients %} select '{{ client }}' as client_id, * from {{ source(source_name ~ '_' ~ client, table_name) }} {% if not loop.last %} union all {% endif %} {% endfor %} {% endmacro %}
Tech decisions
  • Incremental models on all fact tables with merge strategy and event-time-based unique_key.
  • LinkedIn URN extraction macro that pulls campaign / creative / account IDs from URN strings (urn:li:sponsoredCampaign:12345) into clean numeric columns.
  • Google Ads campaign-name parser with regex tokens for account, channel, audience, and geo — surfaced as columns the marketing team can group on.
  • dbt_utils / dbt_expectations for referential integrity between deals, contacts, and ad-touchpoint marts.
  • GitHub Actions CI with slim CI (--select state:modified+) so PRs only build affected models against a CI dataset.
Outcome

A working three-layer project with macros that get reused, mart-layer tests that catch the things I would have missed, and column-level docs. Onboarding a new client means adding a row to vars instead of forking the project — which was the whole point.

Lessons

Multi-tenant dbt rewards investing early in conventions: schema names, macro signatures, and source naming. Slim CI was the single biggest unlock for review speed once the project crossed ~30 models.

02
Open source · Claude / MCP

dbt-mcp-server

A Model Context Protocol server that exposes a dbt project's manifest, lineage graph, and test results to Claude — letting analysts ask plain-English questions about model dependencies, downstream impact, and missing documentation.

Python MCP Claude API dbt manifest.json FastAPI
Read the case study
Problem

Even with dbt docs and lineage graphs, certain everyday questions are slow to answer manually: "What's downstream of this source if I rename a column?" · "Which marts have no documentation yet?" · "Why did the test on fct_ad_touchpoints fail this morning?" Clicking through dbt docs is fine; asking is faster.

Approach

Built an MCP server that wraps dbt's manifest.json and run_results.json as a set of tools Claude can call. Each tool answers one specific question and returns structured data the model can summarize naturally.

# Tools exposed by the MCP server get_model_lineage(model_name) # upstream + downstream graph find_orphan_sources() # sources with no downstream models find_undocumented_models() # missing model or column docs summarize_test_failures(since) # last N runs, grouped by model suggest_doc_blocks(model_name) # auto-draft from compiled SQL trace_column_lineage(column, model) # where a column originates
Tech decisions
  • Stateless server — reads target/manifest.json on each tool call so it always reflects the latest dbt parse.
  • Lineage as a graph: parsed once into NetworkX, exposed via subgraph queries.
  • Doc suggestions use Claude itself: server reads a model's compiled SQL, sends it back through the API with a prompt template, returns YAML-ready doc blocks the user can paste into schema.yml.
  • Auth-less local mode for solo devs; HTTP+token mode for team use against a shared dbt project repo.
Outcome

I use it on my own dbt project. Auto-drafting first-pass column docs from compiled SQL has been the biggest win — it's the difference between writing them and not bothering. Lineage questions that took me five minutes of clicking through dbt docs now take five seconds of typing.

Lessons

MCP rewards small, sharp tools. The first version had one giant introspect_dbt tool — it was useless. Splitting it into six narrow tools made Claude's tool selection reliable and the responses crisper.

Older personal project · Web

rails-community-tracker

A community impact tracker built on Rails with a GraphQL API, React frontend, Redis caching, and full Minitest coverage. Older project, not data-stack, but it's where I still go when I want to learn a new tool against something I already understand.

Ruby on Rails GraphQL PostgreSQL Redis React Docker CircleCI
Read the case study
Why this is on the page

It's the project where I first got serious about test coverage, containerization, and CI — the engineering habits that make my data work less chaotic now. The skills transferred better than I expected: GraphQL schemas and dbt sources have more in common than they should, and the muscle memory of "write the test before you trust the code" is the single most useful thing I brought from web work into data.

What's in it
  • Rails GraphQL API backend with a React frontend and Redis caching for the dashboard queries that hit hardest.
  • Full Minitest suite — model, controller, and integration tests — kept honest with a coverage gate in CI.
  • Docker + CircleCI pipeline doing zero-downtime deploys on every merge to main.
  • Role-based access control and audit logging, modeled after compliance patterns in regulated SaaS.
