What I've built.

01 / FULL-STACK

rails-community-tracker

A full-stack community impact tracking application built to mirror the architecture of financial-institution SaaS products. Rails API backend, GraphQL, React frontend, Redis caching.

Ruby on Rails GraphQL ReactJS PostgreSQL Redis Docker Minitest CircleCI

Problem

Financial institutions need to log, categorize, and report community development activities (events, donations, partnerships). Most tracking is done in spreadsheets — hard to query, impossible to aggregate across teams.

Approach

Built a Rails 7 API with a GraphQL layer so frontends can query exactly what they need without over-fetching. Chose React for the dashboard because of its composability — each reporting widget is an independent component. Redis was added to cache expensive aggregate queries that run on every dashboard load.

Technical Decisions

GraphQL mutations for all write operations keep the API surface clean. Minitest was used over RSpec to stay close to Rails conventions and keep the test suite fast. CircleCI pipeline runs the full test suite on every PR and deploys to a staging environment on merge to main. Docker Compose handles local dev, Helm charts manage the production cluster.

Outcome

Full test coverage on all models and resolvers. Redis caching reduced dashboard query time from ~800ms to ~90ms. Pipeline achieves zero-downtime deploys on every release.

Lessons

GraphQL's schema-first design forces you to think about your data model before writing a line of business logic — a discipline that pays dividends throughout the project lifecycle.

02 / INTERNAL TOOL

hospital-workflow-portal

A React + Node.js internal web portal replacing manual spreadsheet shift management for 40+ lab staff across 3 departments, with full Cypress E2E test coverage.

React Node.js PostgreSQL REST APIs Cypress Docker

Problem

Lab shift schedules were managed in shared Excel files — prone to conflicts, with no audit trail and no visibility across departments. Staff spent 30–40 minutes per day reconciling discrepancies manually.

Approach

Replaced the spreadsheet with a React SPA backed by a Node.js/Express API and PostgreSQL. Role-based access ensures each department only sees and edits their own schedules, while supervisors get a cross-department view. The backend integrates with the hospital's existing REST APIs via an adapter layer.

Technical Decisions

Cypress was chosen for E2E testing because the app's value is entirely in the UI interactions — unit tests alone wouldn't catch the class of bugs users actually encounter. The REST adapter includes retry logic and graceful degradation so upstream failures don't surface as errors to users.

Outcome

Cypress suite catches regressions before each release. QA-related delays dropped by ~60%. Daily reconciliation time reduced from 30–40 minutes to near-zero for the 40+ staff using it.

Lessons

Investing in E2E tests early means you can refactor with confidence. Three major internal refactors happened post-launch; Cypress caught regressions each time.
